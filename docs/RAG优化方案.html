核心判断

当前 RAG 的上限不在模型，而在「检索不到 + 证据被丢弃 + 无法度量」。因此优化顺序必须先修链路正确性，再谈召回率提升。在证据都没送到模型面前的时候，换更大的模型是浪费。

1. 优化目标与适用场景

1.1 服务对象与使用场景

维度现状
直接使用者中学生（单机 GUI 问答，student_app/gui_app/）
交互形态自然语言提问 → 流式答案 + 溯源信息 + 可选示意图
典型问法概念解释（"什么是向心力"）、公式/定理理解、教材例题讲解、多轮追问（"为什么""再举个例子"）
间接使用者后续的教师端 / 内容同步（tools/sync_client.py、ingest_manifest）
内容源textbooks/（6 本人教版物理 PDF）、notes/、scripts/data_collection/data/

1.2 硬约束（选型的边界条件，不可忽略）

  1. CPU 单机：目标机型为 i3 级处理器，torch.set_num_threads(2) 与 llama.cpp n_threads=4 会争抢 CPU。
  2. 离线优先：已通过 HF_HUB_OFFLINE + hf-mirror 镜像解决网络问题，新增模型必须能离线缓存。
  3. 上下文窗口小：Qwen2.5-1.5B 加载为 n_ctx=2048，system prompt + 历史 + 证据 + 输出共用这 2048 token。这是"多召回证据"的物理上限。
  4. 内存受限：模型文件约 1.04 GB，SentenceTransformer 在引擎 __init__ 即常驻。再加 reranker 需评估内存。
  5. 无 GPU：所有重排/改写必须按 CPU 延迟定价，交互式问答可容忍的额外延迟上限约 1.5–2 s。

1.3 优化目标（分四层，逐层验收）

层级目标可验证的成功定义
T1 可用性检索"真的能命中"6 本教材全部入库；GUI 每个学科选项都能选中非空集合；数学/英语/计算机不再零上下文
T2 正确性分数语义正确、证据不丢失相似度改用真实余弦；top-k 不再被硬压；检索到的证据完整进入模型
T3 可信性有据可依、可溯源、不编造答案可标注来源块；上下文无支撑时明确拒答而非编造；引用准确率达标
T4 可度量效果可量化、可回归有 ≥100 题评测集；每次参数变更自动出 Recall / 忠实度报告

1.4 适用与不适用场景

本方案适用

  • 教材/教辅这类结构清晰、术语密集、需要精确引用的知识问答。
  • 单机、离线、低配 CPU 环境。
  • 需要"答不出来就说不确定"的教育场景（幻觉的代价高于拒答）。

本方案不适用 / 需另做设计

  • 多跳推理型问题（需要 GraphRAG，本方案仅预留接口，见 §3.4）。
  • 大规模并发服务（当前为进程内单例 + 无锁缓存，见 rag_cache.py）。
  • 多模态（图片、音频）检索，需要单独的视觉/语音链路。
  • 需要强化学习训练生成模型的方案（语雀文档中的 GRPO 证据约束 RL）—— 本地 1.5B + CPU 环境不具备训练条件，本方案以规则与 Prompt 约束替代，并在 §6 中说明取舍。

2.2 关键问题清单

问题按「严重程度 × 修复成本」排序。每条均给出代码证据，可逐条复核。

A. 知识工程与入库 P0

A1｜知识覆盖率断裂：6 本教材只入库 2 本

  • 现象：textbooks/ 下有 6 个物理 PDF，向量库中只有 2 本。
  • 证据：mati_data/chroma_db/chroma.sqlite3 实测 —— neb_science：226 块（人教版物理必修二 171 块，id 0–170；必修三 55 块，id 171–225）；neb_readme：5 块（textbooks/README.md）；合计 231 块，库体积 8.7 MB。
  • 影响：询问其余 4 本教材的内容时，检索必然落空，模型退化为纯参数化回答 —— 这是当前"答不准"最直接的原因。
  • 次生问题：neb_readme 是 README 文本，会污染检索结果（空 subject 时 neb_ 前缀可命中所有集合）。

A2｜学科路由指向不存在的集合，数学/英语/计算机完全无上下文

  • 证据：rag_retrieval_engine.py:119-135 的 subject_map 引用了 openstax_science、scienceqa、finemath、gsm8k、cs_stanford、fineweb_edu、khanacademy_pedagogy 共 7 个集合，而 DB 中只有 neb_science 和 neb_readme。main_window.py:38-44 的 GUI 学科键与 map 的键也未完全对齐（如 GUI 的 English Grammar vs map 的 english）。
  • 影响：实测除 Science 外，Math / Mathematics / Computer Science / English Grammar 等全部返回空集合 → 检索为空 → 直接进入纯 LLM 生成。三层 fallback（:148-155）同样因为集合不存在而失效。

A3｜年级维度形同虚设

  • 证据：query() 签名（rag_retrieval_engine.py:160-168）没有 grade 参数，内部固定传 ""（:244）；_get_relevant_collections 中 neb_{subject}_grade_{grade} 因此永远匹配不上，只剩 startswith 兜底；摄取侧 extract_metadata（ingest_content.py:337-349）从文件名解析年级，2025人教版物理必修二.pdf 无法解析出 1–12 的数字 → grade="unknown"，DB 内实测所有块 grade 均为 unknown；查询也没有 where= 元数据过滤。
  • 影响：文档承诺的"按学科 + 年级过滤"在代码中不存在。anti_confusion_engine.py:104-107 的年级加权分支因 grade_str 是 "unknown" 而恒不命中。

A4｜ingest_directory 路径存在跨文件 ID 覆盖缺陷（潜在，尚未爆发）

  • 证据：ingest_content.py:421 — ids = [f"{collection_name}_{i}" for i in range(len(chunks))]，ID 仅由「集合名 + 块序号」组成，不含文件名或内容哈希。配合 upsert（:433），同一集合内第二个文件的 _0..._n 会覆盖第一个文件的同序号块。
  • 当前为何没炸：现有索引 ID 是连续的 0–170 / 171–225，说明它是由 ingest_manifest 路径写入的（该路径使用包内预分配的全局唯一 chunk["id"]，见 tools/package_builder.py:163）。
  • 风险：一旦用 python scripts/ingest_content.py --input textbooks 走目录摄取路径补齐另外 4 本教材，已入库的 2 本会被静默覆盖。

A5｜入库内容含噪声，无清洗与去重

  • 证据：抽取到的块中包含封面版权页、目录、图注、页码等。例如某块内容为 "全国优秀教材二等奖\n物理\n第二册\n必 修..."，另一块是整页目录。
  • 影响：这类块与用户问题语义距离近（都含学科词汇），容易被召回并占用本就紧张的上下文预算。无任何去重逻辑（既无哈希去重也无语义去重）。

A6｜分块参数三处不一致

  • 摄取侧：EnhancedChunker(chunk_size=512, overlap_ratio=0.1)（ingest_content.py:114）
  • Chunker CLI 默认：--overlap 0.2（enhanced_chunker.py:438）
  • 文档宣称："512 token / 10% 重叠"（readme.md:183、HOW_TO_PROCESS.md:163），实际单位是字符数而非 token（enhanced_chunker.py:55）。

B. Chunk 切分 P0 —— 最技术性、也最容易被忽视的问题

B1｜中文句子边界识别完全失效，实际退化为"每 512 字符硬切"

证据：enhanced_chunker.py:175

for match in re.finditer(r'[.!?]\s+', text):
  • 字符类里没有中文标点（。、！、？、；）；
  • 即使补上中文标点，\s+ 要求标点后必须有空白字符，而中文行文标点后通常直接接字；
  • 兜底逻辑（:264-268）用 text.rfind(' ') 找空格，中文段落内没有空格 → safe_split 保持 target_end 不变 → 直接按 512 字符切断。

影响："Math-aware chunking" 的设计意图在中文文档上完全落空。一个完整的定理陈述、一道例题的题干与解析、一段公式推导，都会被 512 字符的硬边界从中间切开。这正是语雀文档强调的 "切块策略导致上下文不连贯，步骤 A/B 被拆分无法一起召回" 的原型。

B2｜没有任何结构感知切分

  • PDF 抽取后直接进 chunker，章节标题、小节号、例题标记、图注均未被识别为结构信号。
  • Markdown 标题（#/##）在 smart_chunk_with_overlap 内未被利用，只有 chunk_markdown_file 会解析 YAML frontmatter（:332-345），而 ingest_directory 根本没走这个函数。

B3｜无父子索引 —— 召回单元 = 生成单元，二者被绑死在 512 字符。语雀文档给出的解法正是父子索引：子块（小、精准）用于召回，父块（大、完整语义）用于喂给 LLM。

C. Query 改写 P1

C1｜只有"纠错"，没有"改写"

  • 现有能力是 AdaptiveNormalizer（system/input_processing/adaptive_normalizer.py）—— 拼写纠正、口语化归一、语种检测、低置信样例落盘（low_confidence_cases.jsonl）。
  • 没有：同义扩展（"自由落体" ↔ "自由下落"）、术语规范化、子问题拆解（"平抛运动的规律和斜抛有什么区别" 是两个问题）。
  • 额外问题：GUI 先归一化一次，引擎内 rag_retrieval_engine.py:205 又用 AdaptiveNormalizer 归一化一次，同一问题被归一化两遍，第二次的输入已是改写结果，可能引入二次偏差。

C2｜已有反馈数据但未接入改写 —— pattern_miner.py + low_confidence_cases.jsonl 已经是一套低置信样例挖掘机制，但没有与检索失败（零召回/低分）关联，无法形成"改写策略 ← 检索效果"的闭环。

D. 检索召回 P0 / P1 —— 召回能力被三重削弱

D1｜top-k 被硬压到 2

证据：rag_retrieval_engine.py:257

n_results=min(2, n_results)

调用链上 main_window.py:803 根本不传 n_results，所以取默认 3 → min(2, 3) = 2。即使路由到 3 个集合，候选池也只有 6 条。6 条候选里再按字符数截到 1600、按阈值 0.35 过滤，实际进入模型的往往只有 1–2 条。对比语雀方法论：工业级方案候选池通常是 20–50 条，当前比业界小一个数量级。

D2｜相似度分数语义错误：用 1 − L2距离 冒充余弦相似度

  • rag_retrieval_engine.py:266 — 'score': 1.0 - res['distances'][0][i]
  • 集合 schema 实测为 "space":"l2"（chroma.sqlite3 的 collections.schema_str），HNSW 参数 ef_construction=100, max_neighbors=16, ef_search=100。
  • 下游 anti_confusion_engine.py:96 注释与命名把它当余弦用（# Cosine similarity）。
  • 而缓存侧 rag_cache.py:124 用的是正确的余弦（归一化点积）—— 同一系统内两套不一致的相似度度量。
  • 推导：嵌入向量已归一化，L2 距离 d = √(2 − 2cos)，因此 score = 1 − d ≈ 2cos − 1。同向 → 1.0，正交 → −0.414，反向 → −1.0。排序顺序尚能保持（单调），但阈值的物理含义完全错位，且随来源权重漂移（见 D4）。

D3｜纯稠密单路检索，没有关键词召回

  • 没有 BM25、没有 FTS、没有混合检索。对本项目最具体的危害：物理学科有大量术语与符号密集的问法 —— "向心加速度""万有引力常量 G""平抛运动" —— 靠 512 维小模型做语义匹配时容易与近邻概念混淆（"向心力" vs "离心力"）。精确匹配恰恰是 BM25 的强项，而当前完全缺位。
  • 另注：Chroma 内部其实建了文档的 FTS 索引（schema 中 "#document":{"fts_index":{"enabled":true}}，库中亦有 embedding_fulltext_search* 表），但代码完全未使用。

D4｜来源权重压过相关性，导致阈值随来源漂移

  • 证据：anti_confusion_engine.py:102 — weighted_score = (base_score * 0.7) + ((priority_score / 100.0) * 0.3)，来源优先级权重占 30%，远超其应有的"轻微倾斜"作用。
  • 后果（实测推算）：阈值 final_score >= 0.35（rag_retrieval_engine.py:284）
    • NEB 来源块（priority=100，贡献 0.3）：需要 1-d ≥ 0.0714 → 约 cos ≥ 0.57
    • 外部来源块（priority=60，贡献 0.18）：需要 1-d ≥ 0.243 → 约 cos ≥ 0.71
    → 同一个"相关性阈值"，对不同来源实际执行了不同的严格程度。由于 A5 已证实库中存在大量噪声块，一条相关性仅 0.57 的 NEB 噪声块（如封面页、目录页）能通过，而一条相关性 0.65 的优质外部块会被丢弃 —— 这个偏差是实际在起作用的。

D5｜学科路由与集合命名耦合脆弱 —— 集合名由文件名推断（ingest_content.py:351-360）；neb_readme 这类"意外集合"会因 neb_ 前缀兜底被命中（rag_retrieval_engine.py:112）。

D6｜HNSW 参数为默认值，未针对小库调优 —— 库仅 231 条向量，本可把 ef_search 从 100 提到 200–400 几乎零成本换取更高召回；反而在候选池仅 2 条的情况下，其收益被 top-k 硬压完全吃掉。

E. 上下文组装与截断 P0 —— 这里丢掉的证据最多

E1｜两次截断，证据被丢弃 >45%，且第二次是静默的
位置限制单位
rag_retrieval_engine.py:281limit = 1600字符
qwen_handler.py:100-108len(context) > 850 → 截断字符

检索层辛苦凑到 1600 字符的证据 → 拼成 full_context_str → get_answer_stream() → _build_prompt 里发现超过 850 就直接砍掉一半，只保留前 850 字符并在句号处对齐。这意味着辛苦召回的证据有一半以上从未到达模型，而且这个截断没有任何日志、没有降级提示，从上层完全不可观测。

E2｜截断策略用 break 而非 continue，高分块可能被跳过

for chunk in ranked_chunks:
    if chunk['final_score'] < 0.35: continue
    if current_len + len(text) < limit or not final_context_chunks:
        final_context_chunks.append(chunk); current_len += len(text)
    else:
        break                      # ← 一旦某块放不下，后面所有块全部放弃

若第 3 个块较长导致超限，则第 4、5 个块（可能分数更高或被 resolve_conflicts 排到前面的 NEB 块）被无条件丢弃。正确做法是 continue 并优先保留高价值块。

E3｜"证据价值"未参与保留决策 —— 语雀文档明确要求截断时优先保留：关键规则、条件限制、操作步骤、URL、安全边界。当前实现是纯粹的"分数降序 + 先到先得"，没有任何结构化信号的参与。

E4｜字符预算 ≠ token 预算 —— 全部用字符数（1600 / 850 / 512），而模型的实际约束是 token（n_ctx=2048，max_tokens=768）。中英混排、公式、LaTeX 的字符-token 比差异很大，用字符数无法保证不超窗。

F. 排序 Rerank P1

  • F1｜没有真正的重排模型 —— 没有 cross-encoder / reranker。rank_results 是特征线性加权（相似度 0.7 + 来源 0.3 + 年级条件 +0.1）。语雀文档强调 rerank 的作用是"把最有用的证据放到模型最容易看到的位置"，而线性加权只能做粗排。
  • F2｜resolve_conflicts 名不副实 —— anti_confusion_engine.py:174-181 实现只是把 source_type == 'NEB' 的块整体前移，是稳定划分，不是冲突消解。真正的知识冲突（同一概念不同教材版本表述不一致、旧版残留下线文档仍被召回）完全没有治理。这是语雀文档指出的"错答占比最高的环节（知识冲突 45.8%）"。
  • F3｜年级加权是死分支 —— anti_confusion_engine.py:104-107 要求 str(metadata['grade']) in query_text，而 grade 全为 "unknown"，用户提问也不会包含 "unknown" → 永不命中。

G. 可信生成与幻觉防控 P2

G1｜"防幻觉"第 4 层是死代码

anti_confusion_engine.py 的类 docstring 声明了 5 层防御，其中 Layer 4: Strict Grounding (Hallucination Prevention) 对应 validate_grounding()（:121-172）。全仓库检索确认：validate_grounding 与 filter_low_quality 没有任何调用点。也就是说，声明的防幻觉机制从未生效。

而且即便接上也是无效的：实现用 re.findall(r'\b\w{5,}\b', answer_lower) 提取"关键词"，依赖 \b 词边界 —— 中文没有空格词边界，这个正则在中文上会退化成把连续汉字整段匹配，overlap 比例计算失真；黑名单也全是英文短语。

G2｜Prompt 约束是唯一实际生效的护栏 —— qwen_handler.py:30-40 的 system prompt 要求"优先依据参考材料""若材料不足先说明未找到"。这是当前唯一的可信性保障，强度依赖 1.5B 模型的指令跟随能力。无引用标记（citation）、无 URL 校验、无输出后校验。

G3｜置信度恒为 0.3（中文分词缺陷）

  • 证据：rag_retrieval_engine.py:359-374，流式路径在 :315 调用它：
if not answer or len(answer.split()) < 5:
    return 0.3
  • 中文答案无空格 → answer.split() 返回 1 个元素 → < 5 成立 → 恒定返回 0.3。
  • 对照：qwen_handler.py:148-156 已经实现了 CJK 感知的 _units()（每个汉字算一个单位），但流式路径没有复用它。
  • 影响：GUI 展示的置信度是恒定值，完全没有信息量；也失去了"低置信 → 触发人工复核/拒答"的抓手。

4.3 关键技术要点与坑

  1. 改 hnsw:space 必须重建索引，HNSW 索引不支持原地改度量。所以步骤 1.1 与 1.3 必须合并执行。
  2. Chroma upsert 的 ID 语义：ID 是覆盖键，不是自增键。任何"集合名 + 序号"式的 ID 方案在目录批量摄取下都是 bug（见 A4）。
  3. get_or_create_collection 不会更新已存在集合的 metadata：想改 hnsw:space 或 HNSW 参数，必须先删集合再建。
  4. 中文正则的三重陷阱：\b 无词边界、\s 匹配不到标点后的零宽位置、\w 会把整段汉字当一个词。凡是面向中文的分词/断言/校验，都要用显式字符类（[\u4e00-\u9fff]）或 jieba。
  5. 父子索引的召回-生成解耦：子块用于召回（精准），父块用于生成（完整）。不要用父块做召回，否则向量会被稀释、相似度下降。
  6. RRF 的 k 值：k=60 是经验值；k 越大越平缓。不要用"分数归一化后加权求和"，因为多路分数尺度不可比（本项目已经踩过这个坑）。
  7. token 预算要用实测校准：先用启发式（中文 1 字 ≈ 1 token）跑通，再用几组长文本对比估算误差，必要时才引入 tokenizer。
  8. LLM-as-judge 用本地 Qwen 时：temperature=0.1、要求严格 JSON 输出、并抽样人工校准一致性，否则评分本身不可信。
  9. 离线模型加载：任何新增资源（jieba 词典、reranker、BM25 语料）都要走"本地缓存优先 + hf-mirror 兜底"的既有模式，避免破坏离线能力。
  10. 别碰的两件事：① 不要为了提升召回而无限加大 chunk 数量（上下文预算有限，噪声会挤掉真信号）；② 不要在链路未修正前更换更大的生成模型（收益会被上游问题淹没）。

关于"证据约束强化学习"的取舍说明

语雀文档中的 GRPO + 多奖励（Evidence Faithfulness / Style / Safety / URL Validity）需要训练资源。本地 1.5B + CPU 环境不具备训练条件，本方案以三条替代路径达成同等目标：

  1. 确定性规则兜底（引用校验、URL 校验、拒答策略）—— 比训练更可靠，且可解释；
  2. Prompt 硬约束（system prompt 已有基础，继续强化）；
  3. 输出后校验 + 置信度联动。

若将来有 GPU 资源，可直接在阶段四的评测集上做 LoRA 微调（Query 改写或答案忠实度），评测框架已就位。
