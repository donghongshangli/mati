## 0. 一页速览

| 环节 | 现状 | 最关键的问题 | 优化策略 | 优先级 |
|------|------|-------------|---------|--------|
| 知识工程（入库） | 2 个集合、231 块、2/6 本教材 | 学科覆盖断裂；元数据只有 4 个字段且 `grade` 全为 `unknown` | 全量重建索引 + 元数据补全 + 内容去噪 | **P0** |
| Chunk 切分 | 512 字符 / 10% 重叠 | **中文句子边界正则失效 → 实际按 512 字符硬切** | 中文标点感知 + 标题层级 + 父子索引 | **P0** |
| Query 改写 | 仅错别字/口语纠正 | 无同义扩展、无子问题拆解 | 术语同义词表 + 小模型改写兜底 | P1 |
| 检索召回 | 纯稠密单路，每集合只取 2 条 | **top-k 被硬压到 2**；相似度用 `1 - L2距离` 冒充余弦 | 放宽 top-k + BM25 混合召回 + RRF 融合 | **P0/P1** |
| 排序 Rerank | 线性加权，来源权重占 30% | 来源权重压过相关性；**阈值随来源漂移** | 特征加权重排 + 可选 cross-encoder | P1 |
| 上下文截断 | 1600 字符 → 再截 850 字符 | **二次截断丢弃 >45% 证据**；`break` 丢高分块 | 统一 token 预算 + 价值排序保留 | **P0** |
| 可信生成 | Prompt 约束 + 死代码校验 | **`validate_grounding` 从未被调用**；中文失效 | 引用标记 + 中文忠实度校验 + 拒答策略 | P2 |
| 评估闭环 | 无评测集 | 只有 18 个"返回 dict"式结构断言 | 建评测集 + 分阶段评测 + 反馈回流 | P2/P3 |
| 系统指标 | 置信度恒 0.3 | **中文 `split()` 数词导致置信度失真** | 复用已有 CJK 感知分词 | **P0** |

**核心判断：当前 RAG 的上限不在模型，而在"检索不到 + 证据被丢弃 + 无法度量"。因此优化顺序必须先修链路正确性，再谈召回率提升。**

## 1. 优化目标与适用场景

### 1.1 服务对象与使用场景

| 维度 | 现状 |
|------|------|
| 直接使用者 | 中学生（单机 GUI 问答，`student_app/gui_app/`） |
| 交互形态 | 自然语言提问 → 流式答案 + 溯源信息 + 可选示意图 |
| 典型问法 | 概念解释（"什么是向心力"）、公式/定理理解、教材例题讲解、多轮追问（"为什么""再举个例子"） |
| 间接使用者 | 后续的教师端 / 内容同步（`tools/sync_client.py`、`ingest_manifest`） |
| 内容源 | `textbooks/`（6 本人教版物理 PDF）、`notes/`、`scripts/data_collection/data/` |

### 1.2 硬约束（选型的边界条件，不可忽略）

1. **CPU 单机**：目标机型为 i3 级处理器，`torch.set_num_threads(2)`、llama.cpp `n_threads=4`，两者会争抢 CPU。
2. **离线优先**：已通过 `HF_HUB_OFFLINE` + `hf-mirror` 镜像解决网络问题，新增模型必须能离线缓存。
3. **上下文窗口小**：Qwen2.5-1.5B 加载为 `n_ctx=2048`，system prompt + 历史 + 证据 + 输出共用这 2048 token。**这是"多召回证据"的物理上限**。
4. **内存受限**：模型文件约 1.04 GB，`SentenceTransformer` 在引擎 `__init__` 即常驻。再加 reranker 需评估内存。
5. **无 GPU**：所有重排/改写必须按 CPU 延迟定价，交互式问答可容忍的额外延迟上限约 **1.5–2 s**。

### 1.3 优化目标（分四层，逐层验收）

| 层级 | 目标 | 可验证的成功定义 |
|------|------|-----------------|
| **T1 可用性** | 检索"真的能命中" | 6 本教材全部入库；GUI 每个学科选项都能选中非空集合；数学/英语/计算机不再零上下文 |
| **T2 正确性** | 分数语义正确、证据不丢失 | 相似度改用真实余弦；top-k 不再被硬压；检索到的证据完整进入模型 |
| **T3 可信性** | 有据可依、可溯源、不编造 | 答案可标注来源块；上下文无支撑时明确拒答而非编造；引用准确率达标 |
| **T4 可度量** | 效果可量化、可回归 | 有 ≥100 题评测集；每次参数变更自动出 Recall / 忠实度报告 |

### 1.4 适用与不适用场景

**本方案适用**
- 教材/教辅这类**结构清晰、术语密集、需要精确引用**的知识问答。
- 单机、离线、低配 CPU 环境。
- 需要"答不出来就说不确定"的教育场景（幻觉的代价高于拒答）。

**本方案不适用 / 需另做设计**
- 多跳推理型问题（需要 GraphRAG，本方案仅预留接口，见 §3.5）。
- 大规模并发服务（当前为进程内单例 + 无锁缓存，见 `rag_cache.py`）。
- 多模态（图片、音频）检索，需要单独的视觉/语音链路。
- 需要强化学习训练生成模型的方案（语雀文档中的 GRPO 证据约束 RL）——**本地 1.5B + CPU 环境不具备训练条件，本方案以规则与 Prompt 约束替代，并在 §6 中说明取舍**。

## 2. 当前 RAG 流程与关键问题诊断

### 2.1 现状链路

```
用户提问
  │
  ├─ [GUI] normalize 一次（AdaptiveNormalizer）              ← 归一化 #1
  │
  └─ RAGRetrievalEngine.query(query_text, subject, ...)
        │  ※ 无 grade 参数
        ├─ edge_case_handler.check_edge_cases()               ← 兜底
        ├─ normalize 第二次（AdaptiveNormalizer）              ← 归一化 #2（重复）
        ├─ RAGCache.get() / find_similar(0.88)                 ← 缓存
        ├─ _get_relevant_collections(subject, "")             ← 学科路由（grade 传空串）
        │     └─ subject_map 指向 7 个 DB 中不存在的集合
        ├─ embedding_gen.generate_query_embeddings()           ← 加 BGE 查询指令，归一化
        ├─ 逐集合 query(n_results=min(2, n_results))           ← top-k 硬压到 2
        │     score = 1.0 - L2_distance                        ← 分数语义错误
        ├─ anti_confusion.rank_results()                       ← 线性加权：0.7*相似度 + 0.3*来源
        ├─ 阈值过滤 final_score >= 0.35（字符累计 1600 后 break）
        ├─ anti_confusion.resolve_conflicts()                  ← 仅把 NEB 排前面
        └─ qwen_handler.get_answer_stream()
              └─ context 再截断到 850 字符                      ← 二次截断
                    ↓
                 流式答案 + confidence（恒 0.3）
```

### 2.2 关键问题清单

问题按「严重程度 × 修复成本」排序。每条均给出代码证据，可逐条复核。

#### A. 知识工程与入库（P0）

**A1｜知识覆盖率断裂：6 本教材只入库 2 本**

- **现象**：`textbooks/` 下有 6 个物理 PDF，向量库中只有 2 本。
- **证据**：`mati_data/chroma_db/chroma.sqlite3` 实测——
  - `neb_science`：226 块（人教版物理必修二 171 块，id `0–170`；必修三 55 块，id `171–225`）
  - `neb_readme`：5 块（`textbooks/README.md`）
  - 合计 231 块，库体积 8.7 MB
- **影响**：询问其余 4 本教材的内容时，检索必然落空，模型退化为纯参数化回答——**这是当前"答不准"最直接的原因**。
- **次生问题**：`neb_readme` 是 README 文本，会污染检索结果（空 subject 时 `neb_` 前缀可命中所有集合）。

**A2｜学科路由指向不存在的集合，数学/英语/计算机完全无上下文**

- **证据**：`rag_retrieval_engine.py:119-135` 的 `subject_map` 引用了 `openstax_science`、`scienceqa`、`finemath`、`gsm8k`、`cs_stanford`、`fineweb_edu`、`khanacademy_pedagogy` 共 7 个集合，而 DB 中只有 `neb_science` 和 `neb_readme`。`main_window.py:38-44` 的 GUI 学科键与 map 的键也未完全对齐（如 GUI 的 `English Grammar` vs map 的 `english`）。
- **影响**：实测除 `Science` 外，`Math` / `Mathematics` / `Computer Science` / `English Grammar` 等全部返回空集合 → 检索为空 → 直接进入纯 LLM 生成。三层 fallback（`:148-155`）同样因为集合不存在而失效。

**A3｜年级维度形同虚设**

- **证据**：
  - `query()` 签名（`rag_retrieval_engine.py:160-168`）**没有 `grade` 参数**，内部固定传 `""`（`:244`）。
  - `_get_relevant_collections` 中 `neb_{subject}_grade_{grade}` 因此永远匹配不上，只剩 `startswith` 兜底。
  - 摄取侧 `extract_metadata`（`ingest_content.py:337-349`）从文件名解析年级，`2025人教版物理必修二.pdf` 无法解析出 1–12 的数字 → `grade="unknown"`；DB 内实测**所有块 grade 均为 `unknown`**。
  - 查询也没有 `where=` 元数据过滤。
- **影响**：文档承诺的"按学科 + 年级过滤"在代码中不存在。`anti_confusion_engine.py:104-107` 的年级加权分支因 `grade_str` 是 `"unknown"` 而恒不命中。

**A4｜`ingest_directory` 路径存在跨文件 ID 覆盖缺陷（潜在，尚未爆发）**

- **证据**：`ingest_content.py:421` — `ids = [f"{collection_name}_{i}" for i in range(len(chunks))]`，ID 仅由「集合名 + 块序号」组成，**不含文件名或内容哈希**。配合 `upsert`（`:433`），同一集合内第二个文件的 `_0..._n` 会覆盖第一个文件的同序号块。
- **当前为何没炸**：现有索引 ID 是连续的 `0–170` / `171–225`，说明它是由 `ingest_manifest` 路径写入的（该路径使用包内预分配的全局唯一 `chunk["id"]`，见 `tools/package_builder.py:163`）。
- **风险**：一旦用 `python scripts/ingest_content.py --input textbooks` 走目录摄取路径补齐另外 4 本教材，**已入库的 2 本会被静默覆盖**。

**A5｜入库内容含噪声，无清洗与去重**

- **证据**：抽取到的块中包含封面版权页、目录、图注、页码等。例如某块内容为 `"全国优秀教材二等奖\n物理\n第二册\n必 修..."`，另一块是整页目录（`"第五章 抛体运动\n1.曲线运动..."`）。
- **影响**：这类块与用户问题语义距离近（都含学科词汇），容易被召回并占用本就紧张的上下文预算。无任何去重逻辑（既无哈希去重也无语义去重）。

**A6｜分块参数三处不一致**

- 摄取侧：`EnhancedChunker(chunk_size=512, overlap_ratio=0.1)`（`ingest_content.py:114`）
- Chunker CLI 默认：`--overlap 0.2`（`enhanced_chunker.py:438`）
- 文档宣称：`"512 token / 10% 重叠"`（`readme.md:183`、`HOW_TO_PROCESS.md:163`）
- 实际单位是**字符数**而非 token（`enhanced_chunker.py:55`）。

#### B. Chunk 切分（P0 —— 最技术性、也最容易被忽视的问题）

**B1｜中文句子边界识别完全失效，实际退化为"每 512 字符硬切"**

- **证据**：`enhanced_chunker.py:175`
  ```python
  for match in re.finditer(r'[.!?]\s+', text):
  ```
  - 字符类里**没有中文标点**（`。`、`！`、`？`、`；`、`·`）；
  - 即使补上中文标点，`\s+` 要求标点后必须有空白字符，而中文行文标点后通常直接接字。
  - 兜底逻辑（`:264-268`）用 `text.rfind(' ')` 找空格，**中文段落内没有空格** → `safe_split` 保持 `target_end` 不变 → 直接按 512 字符切断。
- **影响**：`"Math-aware chunking"` 的设计意图在中文文档上完全落空。一个完整的定理陈述、一道例题的题干与解析、一段公式推导，都会被 512 字符的硬边界从中间切开。这正是语雀文档强调的 **"切块策略导致上下文不连贯，步骤 A/B 被拆分无法一起召回"** 的原型。
- **可验证的佐证**：同一物理概念的正文被切在 `"...当质点从B点运动到A点，则质点的平均速度的方"` / `"向由B点指向A点..."` 这类位置。

**B2｜没有任何结构感知切分**

- PDF 抽取后直接进 chunker，**章节标题、小节号、例题标记、图注均未被识别为结构信号**。
- Markdown 标题（`#`/`##`）在 `smart_chunk_with_overlap` 内未被利用，只有 `chunk_markdown_file` 会解析 YAML frontmatter（`:332-345`），而 `ingest_directory` 根本没走这个函数。
- **影响**：无法做父子索引，也无法用"章节"作为检索过滤条件。

**B3｜无父子索引**

- 召回单元 = 生成单元，二者被绑死在 512 字符。
- 语雀文档给出的解法正是**父子索引**：子块（小、精准）用于召回，父块（大、完整语义）用于喂给 LLM。

#### C. Query 改写（P1）

**C1｜只有"纠错"，没有"改写"**

- 现有能力是 `AdaptiveNormalizer`（`system/input_processing/adaptive_normalizer.py`）——拼写纠正、口语化归一、语种检测、低置信样例落盘（`low_confidence_cases.jsonl`）。
- **没有**：同义扩展（"自由落体" ↔ "自由下落"）、术语规范化（"离心力" → 教材用的"向心力"）、子问题拆解（"平抛运动的规律和斜抛有什么区别" 是两个问题）。
- **额外问题**：GUI 先归一化一次（`main_window.py`），引擎内 `rag_retrieval_engine.py:205` 又用 `AdaptiveNormalizer` 归一化一次，**同一问题被归一化两遍**，第二次的输入已是改写结果，可能引入二次偏差。

**C2｜已有反馈数据但未接入改写**

- `pattern_miner.py` + `low_confidence_cases.jsonl` 已经是一套低置信样例挖掘机制，但没有与检索失败（零召回/低分）关联，无法形成"改写策略 ← 检索效果"的闭环。

#### D. 检索召回（P0/P1 —— 召回能力被三重削弱）

**D1｜top-k 被硬压到 2**

- **证据**：`rag_retrieval_engine.py:257`
  ```python
  n_results=min(2, n_results)
  ```
  调用链上 `main_window.py:803` 根本不传 `n_results`，所以取默认 3 → `min(2, 3) = 2`。
- **影响**：即使路由到 3 个集合，候选池也只有 **6 条**。6 条候选里再按字符数截到 1600、按阈值 0.35 过滤，实际进入模型的往往只有 1–2 条。
- **对比语雀方法论**：工业级方案是"多路并行检索后合并、去重、再排序"，候选池通常是 20–50 条。**当前候选池比业界小一个数量级。**

**D2｜相似度分数语义错误：用 `1 - L2距离` 冒充余弦相似度**

- **证据**：
  - `rag_retrieval_engine.py:266` — `'score': 1.0 - res['distances'][0][i]`
  - 集合 schema 实测为 `"space":"l2"`（`chroma.sqlite3` 的 `collections.schema_str`），HNSW 参数 `ef_construction=100, max_neighbors=16, ef_search=100`。
  - 下游 `anti_confusion_engine.py:96` 注释与命名把它当余弦用（`base_score = res.get('score')  # Cosine similarity`）。
  - 而缓存侧 `rag_cache.py:124` 用的是**正确的**余弦（归一化点积）——**同一系统内两套不一致的相似度度量**。
- **推导**：嵌入向量已归一化，L2 距离 `d = √(2 − 2cos)`，因此 `score = 1 − d ≈ 2cos − 1`。同向 → 1.0，正交 → −0.414，反向 → −1.0。
- **影响**：排序顺序尚能保持（单调），但**阈值的物理含义完全错位**，且随来源权重漂移（见 D4）。

**D3｜纯稠密单路检索，没有关键词召回**

- 没有 BM25、没有 FTS、没有混合检索。
- **对本项目的具体危害**：物理学科有大量**术语与符号密集**的问法——"向心加速度""万有引力常量 G""平抛运动"——这些词靠 512 维小模型做语义匹配时容易与近邻概念混淆（"向心力" vs "离心力"、"匀速圆周运动" vs "变速圆周运动"）。**精确匹配恰恰是 BM25 的强项，而当前完全缺位。**
- 另注：Chroma 内部其实建了文档的 FTS 索引（schema 中 `"#document":{"fts_index":{"enabled":true}}`，库中亦有 `embedding_fulltext_search*` 表），但代码完全未使用。

**D4｜来源权重压过相关性，导致阈值随来源漂移**

- **证据**：`anti_confusion_engine.py:102`
  ```python
  weighted_score = (base_score * 0.7) + ((priority_score / 100.0) * 0.3)
  ```
  来源优先级权重占 **30%**，远超其应有的"轻微倾斜"作用。
- **后果（实测推算）**：阈值 `final_score >= 0.35`（`rag_retrieval_engine.py:284`）
  - NEB 来源块（priority=100，贡献 0.3）：需要 `1-d ≥ 0.0714` → 约 **cos ≥ 0.57**
  - 外部来源块（priority=60，贡献 0.18）：需要 `1-d ≥ 0.243` → 约 **cos ≥ 0.71**
  → **同一个"相关性阈值"，对不同来源实际执行了不同的严格程度**。低质量来源反而更容易被过滤掉，看似合理；但反过来，一条相关性仅 0.57 的 NEB 噪声块（如封面页、目录页）能通过，而一条相关性 0.65 的优质外部块会被丢弃。由于 A5 已证实库中存在大量噪声块，这个偏差是**实际在起作用的**。

**D5｜学科路由与集合命名耦合脆弱**

- 集合名由文件名推断（`ingest_content.py:351-360`），中文教材靠关键词表映射到英文学科。
- `neb_readme` 这类"意外集合"会因 `neb_` 前缀兜底被命中（`rag_retrieval_engine.py:112`）。

**D6｜HNSW 参数为默认值，未针对小库调优**

- `ef_search=100`、`max_neighbors=16`、`ef_construction=100` — 全部是 Chroma 默认值。
- 库仅 231 条向量，本可把 `ef_search` 提高到 200–400 **几乎零成本**换取更高召回；反而在候选池仅 2 条的情况下，`ef_search` 的收益被 top-k 硬压完全吃掉。

#### E. 上下文组装与截断（P0 —— 这里丢掉的证据最多）

**E1｜两次截断，证据被丢弃 >45%，且第二次是静默的**

| 位置 | 限制 | 单位 |
|------|------|------|
| `rag_retrieval_engine.py:281` | `limit = 1600` | 字符 |
| `qwen_handler.py:100-108` | `len(context) > 850` → 截断 | 字符 |

- **链路**：检索层辛苦凑到 1600 字符的证据 → 拼成 `full_context_str` → `get_answer_stream(question, full_context_str)` → `_build_prompt` 里**发现超过 850 就直接砍掉一半**，只保留前 850 字符并在句号处对齐。
- **影响**：**检索层与生成层对"上下文预算"的认知不一致，导致辛苦召回的证据有一半以上从未到达模型**。而且这个截断没有任何日志、没有降级提示，从上层完全不可观测。

**E2｜截断策略用 `break` 而非 `continue`，高分块可能被跳过**

- **证据**：`rag_retrieval_engine.py:283-292`
  ```python
  for chunk in ranked_chunks:
      if chunk['final_score'] < 0.35: continue
      if current_len + len(text) < limit or not final_context_chunks:
          final_context_chunks.append(chunk); current_len += len(text)
      else:
          break                      # ← 一旦某块放不下，后面所有块全部放弃
  ```
- **影响**：若第 3 个块较长导致超限，则第 4、5 个块（可能分数更高或被 `resolve_conflicts` 排到前面的 NEB 块）被无条件丢弃。正确做法是 `continue` 并优先保留高价值块。

**E3｜"证据价值"未参与保留决策，只按分数顺序贪心**

- 语雀文档明确要求截断时优先保留：**关键规则、条件限制、操作步骤、URL、安全边界**。
- 当前实现是纯粹的"分数降序 + 先到先得"，没有任何结构化信号的参与。

**E4｜字符预算 ≠ token 预算**

- 全部用字符数（1600 / 850 / 512），而模型的实际约束是 token（`n_ctx=2048`，`max_tokens=768`）。
- 中英混排、公式、LaTeX 的字符-token 比差异很大，用字符数无法保证不超窗。当前依赖"字符数足够小"来间接避免，属于运气而非设计。

#### F. 排序 Rerank（P1）

**F1｜没有真正的重排模型**

- 没有 cross-encoder / reranker。`rank_results` 是**特征线性加权**（相似度 0.7 + 来源 0.3 + 年级条件 +0.1）。
- 语雀文档强调 rerank 的作用是"把最有用的证据放到模型最容易看到的位置"，而线性加权只能做粗排。

**F2｜`resolve_conflicts` 名不副实**

- **证据**：`anti_confusion_engine.py:174-181` — 实现只是把 `source_type == 'NEB'` 的块整体前移，是稳定划分，不是冲突消解。
- **真正的知识冲突**（同一概念不同教材版本表述不一致、旧版残留下线文档仍被召回）**完全没有治理**。这是语雀文档指出的"错答占比最高的环节（知识冲突 45.8%）"。

**F3｜年级加权是死分支**

- `anti_confusion_engine.py:104-107` 要求 `str(metadata['grade']) in query_text`，而 grade 全为 `"unknown"`，且用户提问不会包含 "unknown" → 永不命中。

#### G. 可信生成与幻觉防控（P2）

**G1｜"防幻觉"第 4 层是死代码**

- **证据**：`anti_confusion_engine.py` 的类 docstring 声明了 5 层防御，其中 `Layer 4: Strict Grounding (Hallucination Prevention)` 对应 `validate_grounding()`（`:121-172`）。
- **全仓库检索确认：`validate_grounding` 与 `filter_low_quality`（`:183-184`）没有任何调用点。** 也就是说**声明的防幻觉机制从未生效**。
- **而且即便接上也是无效的**：实现用 `re.findall(r'\b\w{5,}\b', answer_lower)` 提取"关键词"，依赖 `\b` 词边界——中文没有空格词边界，这个正则在中文上会退化成把连续汉字整段匹配，overlap 比例计算失真；黑名单也全是英文短语（`"i don't have that information"` 等）。

**G2｜Prompt 约束是唯一实际生效的护栏**

- `qwen_handler.py:30-40` 的 system prompt 要求"优先依据参考材料""若材料不足先说明未找到"。这是当前唯一的可信性保障，强度依赖 1.5B 模型的指令跟随能力。
- **矛盾点**：prompt 给了"材料中未找到相关信息"的出路，但 `rag_helper.py:133-161` 的 `validate_context_relevance` 又要求必须有重叠——不过该函数同样无调用点。
- 无引用标记（citation）、无 URL 校验、无输出后校验。

**G3｜置信度恒为 0.3（中文分词缺陷）**

- **证据**：`rag_retrieval_engine.py:359-374`，流式路径在 `:315` 调用它：
  ```python
  if not answer or len(answer.split()) < 5:
      return 0.3
  ```
  中文答案无空格 → `answer.split()` 返回 1 个元素 → `< 5` 成立 → **恒定返回 0.3**。
- **对照**：`qwen_handler.py:148-156` 已经实现了 CJK 感知的 `_units()`（每个汉字算一个单位），但**流式路径没有复用它**。
- **影响**：GUI 展示的置信度是恒定值，完全没有信息量；也失去了"低置信 → 触发人工复核/拒答"的抓手。

#### I. 评测能力（P2/P3）

- **无任何评测集、无评测脚本、无指标定义。**
- 唯一相关测试是 `tests/test_rag_retrieval_engine.py`（18 个用例），断言内容是"返回类型是 dict""包含 answer 字段""两次查询 keys 相同"——**只验证不崩溃，不验证召回质量**。测试里还使用 `subject="Computer Science"` 这类会返回空集合的输入，本身就在掩盖 A2 问题。
- 后果：**任何参数改动都无法判断是变好还是变坏**。这是所有优化中最底层的阻塞项。

### 2.3 错因归因（对照语雀方法论）

语雀文档给出的工业级 badcase 归因分布（知识冲突 45.8% / 检索问题 32.4% / Reranker 3.1% / LLM 18.7%）对本项目的启示：

| 环节 | 业界占比 | 本项目预判主因 |
|------|---------|---------------|
| 知识工程 / 冲突 | 45.8% | **A1 覆盖断裂 + A5 噪声 + B1 中文硬切** —— 本项目问题最集中处 |
| 检索问题 | 32.4% | **D1 top-k=2 + D2 分数语义错 + D3 无关键词召回 + D4 阈值漂移** |
| Reranker | 3.1% | F1/F2，占比低，与业界一致，**不应优先投入** |
| LLM | 18.7% | 1.5B 模型能力上限 + G2 仅靠 Prompt + E1 证据被截断（实为检索侧问题） |

**结论**：优先修**知识工程 + 检索 + 截断**（合计影响约 80% 的错答），LLM 能力不是当前瓶颈——**在证据都没送到模型面前的时候，换更大的模型是浪费**。

### 3.3 阶段二（P1）：混合检索 + 融合重排（预计 6–10 天）

> **实施状态（2026-10-02）：已完成**，见 `docs/RAG优化-P1实施记录.md`。
> 实测结论与本节原计划有三处**偏差**，以实施记录为准：
> ① 子问题拆解改用确定性规则（本地 1.5B 生成的延迟超出本项目自定的 1.5–2 s 上限）；
> ② Query 改写的实际收益是**降低误拒率**（−6.1pt），而非本处预期的提升 Recall@10；
> ③ 附带发现并修复了「年级硬过滤导致跨年级内容假拒答」的设计矛盾（跨年级 Recall 0% → 100%）。
> 另需注意：本节把「证据保留率 ≥0.75」列为验收标准，但该指标在 `rerank_k=10` +
> 2000 token 预算下结构性不可达（详见实施记录 §6.1），应改看「证据预算利用率」。

#### 步骤 2.1｜中文感知的结构化切分（本阶段最关键的改动）

- **动作**
  1. 修 `find_sentence_boundaries`（`enhanced_chunker.py:162-182`）：
     ```python
     boundaries = []
     for m in re.finditer(r'[。！？；!?;]\s*', text):      # 中文标点，无需空格
         boundaries.append(m.end())
     for m in re.finditer(r'[.!?]\s+', text):             # 英文标点 + 空白
         boundaries.append(m.end())
     for m in re.finditer(r'\n\s*\n+', text):             # 段落
         boundaries.append(m.start())
     ```
     （注意中文顿号 `、` 不切分，它是列举符而非句界。）
  2. **标题层级切分**：新增结构解析，优先在 Markdown 标题、`第X章`/`第X节`/`X.X` 编号、`例题`/`练习`/`思考与讨论` 等标记处切分。
  3. **父子索引**：父块 = 一个完整小节（800–1600 字符），子块 = 父块内的语义段（256–512 字符）。入库时**子块携带 `parent_id`**，检索命中子块后**取父块喂给 LLM**。
     - Chroma 里只存子块向量（保证召回精度），父块文本存单独集合或同集合以 `doc_type="parent"` 标记。
- **目标文件**：`scripts/rag_data_preparation/enhanced_chunker.py`、`scripts/ingest_content.py`
- **验收**：抽 20 个块人工检查，**没有一句话被从中间切断**；对"平抛运动的规律"这类需要连续上下文的问题，父块能一次给出完整小节。

#### 步骤 2.2｜BM25 关键词召回 + 双路并行

- **动作**
  1. 引入 `jieba`（中文分词）+ `rank_bm25`（纯 Python，零编译依赖，适合离线 CPU）。
  2. 双路并行检索（对照语雀文档的"定向检索 + 通用检索"）：
     - **定向路**：带 `subject`/`grade` 元数据过滤的向量检索（精准，可能漏召回）；
     - **通用路**：不加过滤的向量检索 + BM25 关键词检索（覆盖广，噪声多）。
  3. 两路结果用 **RRF（Reciprocal Rank Fusion）** 融合：
     ```
     score(d) = Σ_routes 1 / (k + rank_route(d))     # k 取 60
     ```
     RRF 只依赖排名不依赖分数尺度，**天然规避了 D2 里"分数语义不一致"这类问题**，非常契合当前多路分数不可比的现状。
- **目标文件**：新增 `system/rag/hybrid_retriever.py`
- **验收**：对 20 个术语型问题（如"万有引力常量"），BM25 路应能稳定召回包含该词的字面块；RRF 融合后的 top-10 与纯向量 top-10 做人工对比，相关性胜出率 ≥ 60%。

#### 步骤 2.3｜特征加权重排（替代"来源权重占 30%"）

- **动作**：重排分数改为**可解释的特征加权**，把来源权重压到 10% 以内：
  ```
  final = w1 * cos_sim            (0.45)
        + w2 * bm25_norm          (0.20)
        + w3 * term_coverage      (0.15)   # 问题关键词在块中的覆盖率
        + w4 * structure_bonus    (0.10)   # 是否命中标题/例题/定义标记
        + w5 * source_priority    (0.05)   # NEB(1.0) > 外部(0.6)
        + w6 * recency/version    (0.05)   # 教材版本新者优先
  ```
  权重写入 `retrieval.yaml`，可调可回归。
- **动作（可选）**：接入 `bge-reranker-base` 做 cross-encoder 精排，**但必须满足**：仅对 top-10 生效、设置 800 ms 硬超时、超时自动降级为特征加权。默认关闭，通过配置开启。
- **验收**：把来源权重从 0.30 降到 0.05 后，重跑评测集，NDCG@10 不应下降、Recall 应上升；日志中不再出现"噪声块因 NEB 权重入选"的案例。

#### 步骤 2.4｜Query 改写（规则优先，模型兜底）

- **动作**
  1. **术语同义词表**（优先，零延迟）：从教材抽取学科术语，人工维护 50–100 组同义映射（"自由落体" ↔ "自由下落"、"圆周运动" ↔ "匀速圆周运动"）。改写时做扩展，多路并查。
  2. **子问题拆解**（规则触发）：检测到"和""以及""分别""区别"等连接词时，用本地 Qwen2.5-1.5B 生成 2–3 个子查询（严格 JSON 输出，`temperature=0.2`），并做缓存。
  3. **反馈挖掘**：把"检索零命中 / 最高分 < 阈值"的问题写入 `retrieval_failures.jsonl`，复用已有的 `pattern_miner.py` 挖高频失败模式，反哺同义词表——**这是本项目已有基础设施能直接复用的地方**。
- **目标文件**：新增 `system/rag/query_rewriter.py`、`mati_data/config/synonyms.yaml`
- **验收**：改写后的多路查询，对"平抛运动和自由落体有什么区别"这类复合问题，Recall@10 对比单路应提升；改写额外延迟 P95 ≤ 1.5 s（含缓存）。

#### 步骤 2.5｜HNSW 与检索参数调优

- **动作**：库规模仍小（< 2000 块），可将 `ef_search` 从 100 提到 200–400（召回提升、延迟几乎不变）；`max_neighbors` 从 16 提到 32 改善小库的图连通性。参数在建集合时写入 `metadata`。
- **验收**：固定查询集，`ef_search` ∈ {100, 200, 400} 对比 Recall@20 与 P95 延迟，选拐点。

## 4. 资源与技术要点

### 4.1 技术选型

| 组件 | 现状 | 建议 | 理由 |
|------|------|------|------|
| 向量库 | ChromaDB（本地持久化） | **保留** | 已集成，库规模小，无迁移必要 |
| 向量度量 | `space=l2` | **改为 `cosine`** | 让 `1-distance` 直接等于余弦，消除 D2 |
| 嵌入模型 | `bge-small-zh-v1.5`（512 维，95 MB） | **保留** | 中文优化、CPU 友好。若召回仍不足，再评估 `bge-base-zh-v1.5`（~400 MB，768 维），但需整库重嵌入 |
| 生成模型 | Qwen2.5-1.5B-Instruct GGUF（~1.04 GB） | **保留** | 已在跑；**当前瓶颈不在它**，换大模型收益低于修检索 |
| 关键词召回 | 无 | **`jieba` + `rank_bm25`** | 纯 Python、无编译、离线可用，完美契合约束 |
| 融合策略 | 无 | **RRF（k=60）** | 只依赖排名，规避多路分数不可比 |
| 重排 | 线性加权（来源占 30%） | **特征加权（来源 ≤ 5%）**，cross-encoder 作为可选开关 | CPU 延迟约束；先做零成本可解释重排 |
| 可选精排 | 无 | `bge-reranker-base`（~1.1 GB），**默认关闭** | 延迟风险高，需实测后再决定（见附录 D 风险） |
| 评测 | 无 | **自建 `eval_rag.py`**，可选 ragas / deepeval | deepeval 依赖较重，CPU 环境建议自建；LLM-as-judge 复用本地 Qwen |

### 4.2 资源预算

### 4.3 关键技术要点与坑

1. **改 `hnsw:space` 必须重建索引**，HNSW 索引不支持原地改度量。所以步骤 1.1 与 1.3 必须合并执行。
2. **Chroma `upsert` 的 ID 语义**：ID 是覆盖键，不是自增键。任何"集合名 + 序号"式的 ID 方案在目录批量摄取下都是 bug（见 A4）。
3. **`get_or_create_collection` 不会更新已存在集合的 metadata**：想改 `hnsw:space` 或 HNSW 参数，必须先删集合再建。
4. **中文正则的三重陷阱**：`\b` 无词边界、`\s` 匹配不到标点后的零宽位置、`\w` 会把整段汉字当一个词。凡是面向中文的分词/断言/校验，都要用显式字符类（`[\u4e00-\u9fff]`）或 jieba。
5. **父子索引的召回-生成解耦**：子块用于召回（精准），父块用于生成（完整）。不要用父块做召回，否则向量会被稀释、相似度下降。
6. **RRF 的 k 值**：k=60 是经验值；k 越大越平缓。不要用"分数归一化后加权求和"，因为多路分数尺度不可比（本项目已经踩过这个坑）。
7. **token 预算要用实测校准**：先用启发式（中文 1 字 ≈ 1 token）跑通，再用几组长文本对比估算误差，必要时才引入 tokenizer。
8. **LLM-as-judge 用本地 Qwen 时**：`temperature=0.1`、要求严格 JSON 输出、并抽样人工校准一致性，否则评分本身不可信。
9. **离线模型加载**：任何新增模型（jieba 词典、reranker、BM25 语料）都要走"本地缓存优先 + hf-mirror 兜底"的既有模式，避免破坏离线能力。
10. **别碰的两件事**：① 不要为了提升召回而无限加大 chunk 数量（上下文预算有限，噪声会挤掉真信号）；② 不要在链路未修正前更换更大的生成模型（收益会被上游问题淹没）。

### 4.4 人力与分工（1 人可完成，建议顺序）

| 阶段 | 主要工作 | 可并行 |
|------|---------|-------|
| 一 | 索引重建、路由、相似度、top-k、截断、置信度 | 与二/三的**评测集标注**并行 |
| 二 | 中文切分、父子索引、混合检索、RRF、重排、改写 | 与一的验证并行 |
| 三 | 元数据、清洗去重、冲突治理、引用校验 | 与二的调参并行 |
| 四 | 评测脚本、分阶段复跑、反馈回流 | 贯穿全程 |

> 唯一建议提前启动的事：**评测集标注**。它不依赖任何代码改动，却决定后面每一步能不能验证收益。

## 5. 评估指标与预期效果

### 5.1 分层指标体系

| 层 | 指标 | 定义 | 目标 |
|----|------|------|------|
| **检索层** | **Recall@10** | top-10 中命中 gold chunk 的问题占比 | ≥ 0.85 |
| | Recall@5 | 同上，k=5 | ≥ 0.75 |
| | MRR@10 | 第一个 gold chunk 排名的倒数均值 | ≥ 0.65 |
| | 路由准确率 | 选中的集合包含 gold 所在集合的比例 | ≥ 0.95 |
| | 零召回率 | 返回空上下文的查询占比 | **= 0**（应有兜底） |
| **证据层** | 证据保留率 | 送入模型的证据 token / 召回的总 token | ≥ 0.70 |
| | 上下文命中率 | 至少有 1 条证据与 gold chunk 重合 | ≥ 0.90 |
| **生成层** | 忠实度 | 答案陈述能被证据支撑的比例（LLM-judge + 人工抽检） | ≥ 0.85 |
| | 引用准确率 | 答案中 `[n]` 标记真实存在于证据中的比例 | ≥ 0.90 |
| | 拒答正确率 | "库中无答案"负样本被正确拒答的比例 | ≥ 0.80 |
| | 误拒率 | 有答案却拒答的比例 | ≤ 0.10 |
| **系统层** | 端到端 P95 延迟 | 提问到首 token / 完整答案 | 首 token ≤ 5 s |
| | 置信度区分度 | 正确组与错误组的置信度均值差 | ≥ 0.15（当前恒 0，**必测得**） |
| | 缓存命中率 | 真实命中率（需先修 H3） | 观测项 |

### 5.2 评测集构建方案

| 项 | 建议 |
|----|------|
| 规模 | 起步 30 题 → 第一阶段 100–120 题 |
| 构成 | 概念型 40%、术语型 25%、步骤/例题型 20%、多跳型 15% |
| 负样本 | 15–20 题"教材中确实没有"的问题 |
| 标注方式 | 脚本先跑 top-20 候选，人工勾选 gold chunk（比从零标注快 3–5 倍） |
| 覆盖 | 6 本教材各 15–20 题，确保每本教材都被评测 |
| 维护 | 回归集随线上反馈自动增长（§4.3） |

### 5.3 基线与目标

> **诚实说明**：项目当前**没有任何评测基线**，因此下表的"基线"列标注为"待测"，不得编造。阶段一的第一个交付物之一就是**建立基线**——只有先量出现状，才能证明后续改进有效。

### 5.4 分阶段预期效果

**阶段一后**（最快可见）
- 6 本教材全部可检索，**"问其他 4 本书完全没反应"的问题消失**。
- 数学/英语/计算机问题不再零上下文。
- 证据不再被静默丢弃一半，答案有据可依的比例显著上升。
- 置信度从"恒定 0.3"变成有区分度的数值，**首次具备"低置信预警"能力**。
- 预期：评测集上的回复可用率（人工判定"答对了且没编造"）**从不可测提升到 60–70%**。

**阶段二后**
- 术语型问题（"万有引力常量"）命中率明显改善（BM25 的贡献）。
- 切分不再破坏句子，需要连续上下文的问题（"平抛运动的规律"）能一次给出完整小节。
- 阈值不再随来源漂移，噪声块入选率下降。
- 预期：**Recall@10 达 0.85 量级，回复可用率 75–85%**。

**阶段三后**
- 答案可溯源（引用标记 + 章节页码）。
- 库中无答案时能正确说"教材中未找到"，而非编造。
- 目录/封面类噪声块不再污染结果。
- 预期：**回复可用率 ≥ 85%，引用准确率 ≥ 0.90，幻觉率 ≤ 5%**。

**阶段四后**
- 每次参数改动都能在分钟级拿到指标对比，**优化从"感觉变好了"变成"数据证明变好了"**。
- 线上点踩自动进入回归集，质量不倒退。

## 6. 风险与回滚

| 风险 | 可能性 | 影响 | 应对 |
|------|-------|------|------|
| 重建索引期间服务不可用 | 高 | 中 | 重建到 `chroma_db_v2`，配置切换，旧库保留可秒回滚 |
| `hnsw:space` 改 cosine 后阈值需重标定 | 高 | 中 | 阈值全部移入 `retrieval.yaml`，用评测集反推而非拍脑袋 |
| 启用 cross-encoder 后延迟超预算 | 中 | 高 | **默认关闭**；开启时设 800 ms 硬超时 + 自动降级为特征加权 |
| 评测集标注工作量被低估 | 高 | 中 | 先做 30 题小集；用"脚本召回 + 人工勾选"降低单题成本 |
| 中文切分改动引入新边界 bug | 中 | 中 | 保留切分前后对照工具，抽检 20 块验证无断句 |
| 语义去重误删有效内容 | 中 | 中 | 阈值从 0.95 起步逐步下调；去重结果先落盘人工确认再入库 |
| 引入 jieba/rank_bm25 破坏离线能力 | 低 | 中 | 二者均为纯本地包，无网络依赖；词典随包分发 |
| 上下文预算管理误算导致超窗 | 中 | 中 | 加运行期断言：组装后的 token 估算不得超过预算，超了则丢最低分块 |
| 1.5B 模型指令跟随不足，引用标记不可靠 | 中 | 中 | **引用由检索层生成、模型只做编号引用**；再加确定性校验兜底 |

**关于"证据约束强化学习"的取舍说明**：语雀文档中的 GRPO + 多奖励（Evidence Faithfulness / Style / Safety / URL Validity）需要训练资源。本地 1.5B + CPU 环境**不具备训练条件**，本方案以三条替代路径达成同等目标：
1. **确定性规则兜底**（引用校验、URL 校验、拒答策略）——比训练更可靠，且可解释；
2. **Prompt 硬约束**（system prompt 已有基础，继续强化）；
3. **输出后校验 + 置信度联动**。
若将来有 GPU 资源，可直接在阶段四的评测集上做 LoRA 微调（Query 改写或答案忠实度），评测框架已就位。

## 附录 A. 元数据 Schema（适配 Mati 版本）

在 `kb-build-kit` 通用模板基础上裁剪，字段名保持英文。

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `doc_id` | string | 是 | 全局唯一，建议 `{source_sha256[:8]}:{chunk_index}` |
| `chunk_id` | string | 是 | Chroma 主键，**必须全局唯一**（修 A4） |
| `parent_id` | string | 否 | 父块 ID（父子索引） |
| `doc_type` | enum | 是 | `child` / `parent` |
| `source_file` | string | 是 | 原始文件名 |
| `source_sha256` | string | 是 | 文件内容哈希，用于增量与去重 |
| `subject` | string | 是 | 学科（英文键，与配置对齐） |
| `grade` | string | 否 | 年级，`unknown` 应尽量避免 |
| `textbook_version` | string | 否 | 教材版本/年份，用于冲突治理 |
| `chapter` | string | 否 | 章节名 |
| `section` | string | 否 | 小节名 |
| `page` | int | 否 | 起始页码，用于溯源展示 |
| `content_type` | enum | 是 | `body` / `example` / `exercise` / `definition` / `figure_caption` / `toc` / `cover` |
| `chunk_index` | int | 是 | 块序号 |
| `token_estimate` | int | 否 | 估算 token 数，供预算管理直接使用 |
| `concept_key` | string | 否 | 概念标识（GraphRAG 预留） |
| `prerequisites` | string[] | 否 | 先修概念（GraphRAG 预留） |
| `owner` | string | 否 | 内容责任方 |
| `status` | enum | 是 | `published` / `archived` |
| `effective_date` | date | 否 | 生效日期 |
| `updated_at` | datetime | 是 | 最后更新时间 |

**检索侧默认过滤条件**：
```
status != "archived"
AND content_type NOT IN ("toc", "cover")
AND doc_type != "parent"        # 父块不参与召回，只在命中子块后取出
```
